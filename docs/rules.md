# Studai 運用ルール

このファイルは、Studai の開発の進め方の正本です。

- Claude Code（エンジニア）は、CLAUDE.md からこのファイルを読み込みます
- claude.ai のプロジェクト（PM・デザイン・レビュー）には、このファイルの写しを置いています
- Notion には、このファイルを図でまとめた図解版を置いています（食い違ったら、このファイルが正しい）
- ルールを変えるときは「10. ルールの変え方」に従い、PR で変更します（変更の履歴が Git に残ります）

## 1. 役割

| 役割 | 担当 | やること |
|---|---|---|
| PM | claude.ai のプロジェクト | 計画、タスク分解、要件定義・基本設計・詳細設計、技術の解説、Claude Code への依頼文、Notion の更新 |
| デザイン | claude.ai のプロジェクト | 画面一覧、画面案、画面仕様 |
| レビュー | claude.ai のプロジェクト | 設計と PR のレビュー（PR の前には Claude Code の reviewer サブエージェントも確認する） |
| エンジニア | Claude Code | 実装、テスト、PR の作成、マージ |
| 作者 | 本人 | 判断、技術の理解、本人にしかできない作業、各役割へのメッセージの受け渡し、push・PR・マージの承認 |

- 役割ごとに別のチャット（タブ）で作業する。チャット同士は会話を共有しないので、決めたことと成果物は必ず Notion かリポジトリに残す
- デザインとレビューは1タスク1チャット、PM はフェーズごとに新しいチャットにする
- Notion（タスク一覧・役割別ページ・工程別ドキュメント）を書くのは PM だけ

## 2. 意思決定の線引き

| 区分 | 内容 |
|---|---|
| 作者が決める（Claude は案と推奨を出して聞く） | 作る機能の範囲、技術構成と使うサービス、お金がかかること、データモデルと画面の流れ、進め方のルール、旧資料から何を引き継ぐか |
| Claude が決めて報告する | 文言、ファイル名・ページ名、タスクの細かい分け方、調べ方 |

## 3. 理解してから進める

技術的なことは、作者が理解してから決める・進める。

1. 解説：初学者向けに説明する（何者か、なぜ必要か、他の選択肢との違い、Studai でどう使うか）。1回15〜30分で読める量に分け、用語は最初に一言で説明する
2. 質問：作者が分からないところを聞く
3. まとめ：作者が自分の言葉で3行にまとめ、Claude が確認する。ここでタスクの「理解」を「理解済み」にする
4. 判断：理解済みになってから、案と推奨を出して作者が決める
5. 記録：まとめは学習メモとして `docs/learning/` に残す

タスク一覧の「理解」が「解説待ち」のタスクは、「理解済み」になるまで判断にも実装にも進まない。

## 4. タスク

- タスクは Notion の「Studai タスク一覧」で管理する
- タスク ID は `TASK-<種類><2桁の連番>`。P：PM・設計、D：デザイン、R：レビュー、E：実装（Claude Code）、H：作者本人の作業
- 番号は 2026-11-21 の作り直しで 01 から振り直した。v1 の旧タスク ID とは別物
- 項目：ステータス、フェーズ（MVP準備／MVP開発／Phase2）、優先度、担当者、理解（不要／解説待ち／理解済み）、依存タスク、期限目安、完了日、証跡（成果物の場所）
- 引き継いだ決定も、証跡を作り直すためにタスクにする
- 役割別ページ（PM・Engineer・Designer・Reviewer・作者）の先頭に、PM が「次にやること」を日付つきで書く

## 5. タスクの流れ

### 5-1. 実装のタスク（Claude Code）

1. 作者：PM の依頼文を Claude Code に渡す
2. Claude Code：develop を最新にして作業用ブランチを作り、実装する。作業しながら progress.md を書く
3. Claude Code：reviewer サブエージェントで確認して直し、依頼文で指示されていれば push して develop 宛ての PR を作る（実行は作者が承認する）。progress.md の完了報告欄を埋め、ステータスと「状態」を「🔵 レビュー待ち（PR #番号）」にする
4. 作者：レビューのタブに「【レビュー】TASK-〇〇 の PR を見て」と伝える
5. レビュー：PR と progress.md を確認し、レビュー記録に書く。直しがあれば Claude Code への修正の依頼文を出す（2 に戻る）。OK なら「マージしてOK」と返す
6. 作者：Claude Code に「マージして」と伝える
7. Claude Code：次の2つをそのタスクの PR にコミットしてから develop にマージし、作業用ブランチを消して、ローカルの develop を最新にする
   - レビュー記録
   - progress.md のステータスと完了報告の「状態」を「✅ 完了（PR #番号 で develop にマージ済み）」にした変更
8. 作者：PM のタブに「TASK-〇〇 終わった」と伝える
9. PM：progress.md とレビュー記録を読み、Notion を完了にして「次にやること」を書く

完了＝レビュー済みで develop にマージ済み。途中で止まったときは、progress.md の完了報告欄に「途中で停止（理由）」と書く。

### 5-2. PM・デザイン・レビューのタスク（claude.ai）

- 成果物はリポジトリの決まった場所（7. を参照）にファイルとして置く
- 終わったら作者が PM に伝え、PM が Notion を更新する
- claude.ai が置いたファイルは、PM の依頼で Claude Code が docs 用の作業用ブランチでコミットし、PR で develop に入れる（いくつかまとめてよい）
- 設計の資料（要件定義・基本設計・詳細設計）は、PM が Notion の「工程別ドキュメント」に書き、作者が承認してから PM がファイルにして置き、Claude Code にコミットを依頼する

### 5-3. 作者のタスク

- 終わったら PM に伝える。技術の理解のタスクは、学習メモが証跡になる

### 5-4. 各タブの始め方

| タブ | 最初のひと言 |
|---|---|
| PM | 「【PM】状況を確認して」 |
| デザイン | 「【デザイン】TASK-D〇〇 をやって」 |
| レビュー | 「【レビュー】TASK-〇〇 の PR を見て」 |
| エンジニア | PM が出した依頼文を貼る |

始めたタブは、Notion のタスクのページと役割別ページ、関係するリポジトリの資料を読んでから作業する。

## 6. Git の運用

| ブランチ | 役割 | 入れ方 |
|---|---|---|
| main | 公開用。Amplify が本番として公開する | リリースのときだけ、develop から PR で入れる |
| develop | 開発の本流（GitHub の既定ブランチ） | 作業用ブランチから PR で入れる |
| 作業用 `<種類>/TASK-<ID>-<slug>` | 1タスク1本。種類は feat・fix・docs・chore | develop から作り、レビュー後に develop へマージして消す |
| `hotfix/<slug>` | 公開後の急ぎの修正 | main から作り、main と develop の両方に入れる |

- main と develop は保護していて、直接 push できない。PR を通してだけ入れる
- タスクを始める前に develop を最新にする
- コミットするのは自分のタスクのファイルだけ。`git add -A` は使わない
- コミットメッセージは Conventional Commits：`<type>(<scope>): <subject>`
- push・PR の作成・マージは、指示があったときだけ行う。実行するときは作者が承認する
- リリース：PM がリリースのタスクを作る → Claude Code が develop → main の PR を作る → レビューが公開前のチェック（個人情報、費用、動作）をする → OK ならマージしてタグ（`v0.1.0` など）を付ける
- 急がない修正は develop で直し、次のリリースで出す

## 7. 記録（証跡）の置き場所

成果物と記録は、必ずリポジトリのファイルとして残す。工程ごとの資料は Notion とリポジトリの両方に残し、どちらを先に書くか（正本）を工程で分ける。

| 工程 | 正本 | 流れ |
|---|---|---|
| 要件定義・基本設計・詳細設計 | Notion の「工程別ドキュメント」 | PM が書き、作者が承認した版を PM がファイルにして、Claude Code がコミットする。実装は承認済みのファイルに従う |
| 実装・単体テスト・結合テスト | リポジトリのファイル | Claude Code が書く。PM が完了報告を受けて、Notion に要約とリンクを書く |

Notion には、ほかにタスクの状態と記録の場所を書く。

| 記録 | 置き場所 | 書く担当 |
|---|---|---|
| 引き継ぎ事項・計画 | `docs/01-product/` | PM |
| 要件定義 | `docs/01-product/requirements.md` | PM（Notion の承認版） |
| 基本設計（DB・API・処理の仕組み） | `docs/03-engineering/basic-design/` | PM（Notion の承認版） |
| 画面一覧・画面仕様 | `docs/02-design/TASK-<ID>-<slug>/` | デザイン |
| 設計判断（ADR） | `docs/03-engineering/adr/<連番4桁>-<kebab-case>.md`（`adr/README.md` の一覧に追加） | PM・エンジニア |
| 詳細設計 | `docs/03-engineering/detailed-design/<機能>.md` | PM（Notion の承認版） |
| タスクの作業記録と完了報告 | `docs/03-engineering/tasks/TASK-<ID>-<slug>/progress.md`（ひな形：`docs/templates/progress.md`） | エンジニア |
| 使い捨ての検証コード | `docs/03-engineering/spikes/TASK-<ID>-<slug>/` | エンジニア |
| 単体テスト | テストコードと `docs/04-quality/tests/unit/<機能>.md`（観点と結果） | エンジニア |
| 結合テスト | テストコードと `docs/04-quality/tests/integration/<シナリオ>.md`（シナリオと結果） | エンジニア |
| レビュー記録（指摘・判断・反映） | `docs/04-quality/reviews/TASK-<ID>-review.md`（reviewer サブエージェントとレビューの結果を同じファイルに書く） | エンジニア・レビュー |
| 学習メモ | `docs/learning/` | 作者・PM |
| AI に任せたこと・作者が判断したこと | `docs/ai-usage.md` | 全員 |

- 画面（`docs/02-design/`）は、デザインが書くファイルが正本。PM が Notion の「02 基本設計」に要約と画面案へのリンクを書く
- ADR は、ファイルが正本。Notion には一覧とリンクを置く
- 設計を直すときは Notion を直し、作者が承認したらファイルも出し直す
- 実装は、develop に入った承認済みのファイルに従う。Notion と食い違っていたら、実装を止めて PM に知らせる
- Claude Code が作業したタスクは、種類にかかわらず progress.md を書く。完了報告欄を埋めるまで完了にしない
- ファイル・フォルダ名は kebab-case

## 8. 公開・非公開と秘密情報

- このリポジトリは公開している。個人的な事情、勤務先のこと、ローカルのパス、Notion の ID、メールアドレスは書かない
- 非公開のメモは `docs/private/`（Git 管理外）に置く
- API キーやシークレットは、コード・ログ・記録・チャットのどこにも書かない。新しい環境変数は `.env.example` にキー名だけ足す
- マージの前に、レビューが公開してよい内容かを確認する

## 9. 費用

- 目標は月600〜1,500円
- 置いておくだけで課金される部品（ALB、NAT ゲートウェイ、常時起動の RDS、Fargate、パブリック IPv4）は使わない。必要なときは月額の目安を示して作者に確認する
- AWS のリソースを追加・変更する提案には、月額の目安を書く
- AWS のリソースを初めて作る前に、費用の上限設定（AWS Budgets、Claude Console の月額上限）を済ませる
- AI 生成には回数制限（1人1日の上限と全体の上限）を入れる

## 10. ルールの変え方

1. どの役割で決めたことでも、作者が PM に「ルール変更：〇〇」と伝える
2. PM がこのファイルを直す依頼文を Claude Code に出し、PR で変更する
3. PM が claude.ai 側の写しと Notion の図解版（トップページの要約を含む）を直す。claude.ai のプロジェクト指示に関わるときは、差し替え文を出す
